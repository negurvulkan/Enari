# v1.0 Upgrade Guide

Dieser Guide beschreibt die noetigen Schritte fuer Projekte, die von einer frueheren Struktur auf die v1.0-Basis wechseln.

## 1. Mehrsprachigkeit auf Locale-Roots umstellen

Frueher:

```php
'content' => array(
    'root' => '01_Weltbau',
),
```

v1.0:

```php
'content' => array(
    'root' => 'content/de',
),
'i18n' => array(
    'defaultLocale' => 'de',
    'fallbackToDefault' => true,
    'locales' => array(
        'de' => array(
            'label' => 'Deutsch',
            'content' => array(
                'root' => 'content/de',
            ),
        ),
        'en' => array(
            'label' => 'English',
            'content' => array(
                'root' => 'content/en',
            ),
        ),
    ),
),
```

Wichtig:

- Jeder Locale-Root ist komplett konfigurierbar.
- Ordnernamen duerfen je Sprache unterschiedlich sein.
- Die URL benutzt immer den echten lokalisierten Pfad der jeweiligen Sprache.

## 2. Inhalte mit `translation_key` versehen

Alle uebersetzbaren Dokumente brauchen einen stabilen `translation_key`, auch Bereichs-Uebersichten und Standalone-Seiten.

Beispiel:

```yaml
title: Overview
translation_key: worldbuilding.languages.overview
```

Ohne `translation_key` gilt ein Dokument als locale-lokal:

- kein Sprachwechsler fuer diese Seite
- kein Cross-Locale-Fallback
- keine sprachuebergreifende Zuordnung im Graphen

## 3. Lokalisierte Ordnerstrukturen spiegeln

Die alte Annahme "gleicher relativer Pfad in jeder Sprache" gilt nicht mehr. Stattdessen zaehlt allein der `translation_key`.

Beispiel:

```text
content/de/01_Weltbau/01_Sprachen/
content/en/01_Worldbuilding/01_Languages/
```

Beide Baeume koennen unterschiedlich benannt sein, solange die Dokumente sauber ueber `translation_key` verbunden sind.

## 4. Standalone-Seiten pro Locale konfigurieren

Wenn es lokalisierte Service-Seiten gibt, muessen sie in `cms/site.config.php` pro Locale eingetragen werden.

Beispiel:

```php
'standalonePages' => array(
    array(
        'source' => 'cms/pages/impressum.md',
        'slug' => 'service/impressum',
        'translationKey' => 'service.impressum',
    ),
),

'i18n' => array(
    'locales' => array(
        'en' => array(
            'standalonePages' => array(
                array(
                    'source' => 'cms/pages/impressum.en.md',
                    'slug' => 'service/impressum',
                    'translationKey' => 'service.impressum',
                ),
            ),
        ),
    ),
),
```

## 5. Theme-Struktur auf Theme-Ordner umstellen

Alte Struktur:

```text
cms/layouts/
assets/styles.css
```

v1.0-Struktur:

```text
themes/<theme>/
  templates/
    layout.tpl
    page.tpl
    components/
  assets/
    theme.css
```

Wichtig:

- Layouts liegen nicht mehr unter `cms/layouts/`.
- Theme-spezifische CSS-, JS- und Bilddateien gehoeren in den jeweiligen Theme-Ordner.
- Wiederverwendbare Basiskomponenten bleiben unter `themes/shared/templates/`.

## 6. Routen und Links anpassen

Neue oeffentliche Routen:

- `/<locale>/`
- `/<locale>/?page=<localized-path>`
- `/<locale>/graph`

Der globale Graph liegt also nicht mehr unter `/graph`, sondern unter einer locale-spezifischen Route wie `/de/graph`.

## 7. Release-Checks vor dem Rollout

Nach der Migration:

```bash
php scripts/validate-content.php
php scripts/smoke-test.php
php scripts/release-check.php --strict
```

Ein Projekt ist v1.0-bereit, wenn:

- der Validator keine Fehler und keine Warnungen mehr meldet
- die Smoke-Suite alle Kernrouten und Themes besteht
- der kombinierte Release-Check gruen durchlaeuft
